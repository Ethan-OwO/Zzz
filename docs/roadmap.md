# Zzz — Roadmap

## 1. 專案概述

**Zzz** 是一個免費、完全不收集使用者資料的睡眠聲音監測**網站**，用來取代需要付費的睡眠監測 App。

使用情境：睡前打開網站，手機一邊充電一邊整晚放在床上或床頭櫃。網站先學習房間的背景噪音（冷氣、風扇等），之後持續保留最近幾秒的音訊緩衝。偵測到明顯高於背景的聲音時，把「觸發前的緩衝 + 事件本身 + 事件後幾秒」錄成一個片段。早上由使用者**手動按停止**，網站在本機做輕量分析，產出當晚報告：事件時間軸、打呼 / 說夢話 / 其他的分類統計，以及選配的翻身動作量。

使用者可以把整晚資料匯出成**一個 zip**（報告、結構化數據、合併好的音檔），丟給任何 AI 進一步提問。

核心原則：
- **零資料收集**：沒有後端、沒有帳號、沒有分析或追蹤、沒有第三方腳本。所有運算都在瀏覽器內完成，音訊只有在使用者自己下載時才離開裝置。
- **每晚獨立**：不保留歷史紀錄。資料只在當晚錄音期間存在瀏覽器裡（防止當機遺失），使用者匯出並確認後就清除。
- **目標平台**：iPhone Safari 與 Android Chrome。筆電不是目標平台。

最終狀態：部署在 Cloudflare Pages 上的純靜態網站，兩個平台的手機都能撐過一整晚，隔天產出報告並匯出 zip。

## 2. 整體架構與技術選擇

**工具鏈與前端**
- Node 24（以 `.node-version` 鎖定）、pnpm。
- Vite + TypeScript + 原生 Web API，不使用 UI 框架。畫面只有三個：設定 / 錄音中 / 報告與匯出。
- 依賴：`fflate`（前端打包 zip）、`@vitejs/plugin-basic-ssl`（本機 HTTPS 開發）。

**部署**
- Cloudflare Pages 純靜態託管。`main` 是正式站，其他分支自動產生 HTTPS 預覽網址。
- 手機實機測試以 Cloudflare Pages 的分支預覽網址為主。本機自簽憑證只用於電腦與 Android 的快速測試，不依賴它測 iOS。
- 用 `_headers` 設定嚴格 CSP（`connect-src 'self'`，不允許任何外部來源），在技術上保證零資料收集。

**音訊管線**
- `getUserMedia`，關閉 `echoCancellation`、`noiseSuppression`、`autoGainControl`。
- `AudioContext` + `AudioWorklet`：降採樣成 16 kHz 單聲道，逐幀計算特徵（RMS dB、頻帶能量、頻譜特徵）。
- 背景噪音基準：滾動時間窗內幀音量的低百分位數，持續更新。
- 事件偵測：門檻 + 遲滯的狀態機，環形緩衝區提供 pre-roll，事件結束後補 post-roll，相鄰事件合併。
- 事件片段以原始 PCM 分塊寫入 **IndexedDB**，邊錄邊存。

**分類**：規則式頻譜特徵，分成打呼 / 說夢話 / 其他。無法確定時歸為「其他」。

**整夜存活**：Screen Wake Lock API 保持螢幕常亮，錄音畫面全黑。`visibilitychange` 時重新取得 wake lock、恢復 AudioContext。中斷的時段記為「未監測時段」並寫進報告。

**動作感測（選配）**：設定頁選「放床上」才啟用，在同一個按鈕手勢裡請求 `DeviceMotionEvent.requestPermission()`。以 30 秒為一個區間計算動作量。選「放床頭櫃」只用聲音。

**匯出**：一個 zip，內容：
- `report.md`：給人和 AI 讀的報告，標出每個事件在 `night.wav` 裡的起訖秒數
- `data.json`：結構化數據
- `night.wav`：所有片段依時間接成一個 16 kHz 單聲道 WAV
- `prompt.md`：不綁定任何一家 AI 的通用提問建議

優先用 Web Share API 分享檔案，不支援時改用 `<a download>` 下載。

**排除的方案**
- 不用 `MediaRecorder` 當錄音來源：各平台輸出格式不同（Chrome 是 webm/opus、Safari 是 mp4/aac），而且無法做 pre-roll。
- 不輸出 mp3：瀏覽器沒有原生 mp3 編碼器，需要額外的 JS 編碼器。
- 不做鬧鐘：行動瀏覽器的自動播放限制讓網頁鬧鐘不可靠。
- 不提供「放身上」選項：手機插著充電線放在身上有安全與發熱疑慮。
- 不用後端、帳號、分析或追蹤腳本。
- 不保留多晚的歷史紀錄。
- 本版不做瀏覽器內 ML 聲音分類模型（YAMNet 類）。M4 完成後再評估。

## 3. 里程碑

### M1 — 專案骨架與部署管線
**交付**：Vite + TS 專案骨架；Cloudflare Pages 自動部署（`main` 正式站、其他分支預覽網址）；`_headers` 裡的嚴格 CSP 與安全標頭，頁面在此 CSP 下零違規。頁面顯示 Zzz 標題與一個「開始」按鈕，確認兩個平台的手機都能透過 HTTPS 開啟。本機要能用與正式環境相同的標頭驗證 CSP。
**依賴**：無。
**👤**：建立 Cloudflare 帳號，在 Cloudflare Pages 連結 `Ethan-OwO/Zzz`（Build command `pnpm build`、Output `dist`），並確認 Web Analytics 沒有開啟。
**風險**：Cloudflare Pages build image 是否支援 Node 24、是否尊重 `packageManager` 指定的 pnpm 版本，要在第一次部署時看 build log 確認。

### M2 — 麥克風擷取與整夜存活驗證（可行性探路）
**交付**：最小可行的錄音頁。關閉三項音訊處理後取得麥克風，跑 AudioWorklet 降採樣到 16 kHz，搭配 Wake Lock 與全黑畫面，處理 `visibilitychange` 的恢復。只把心跳紀錄（每分鐘處理的幀數、AudioContext 狀態、wake lock 狀態）寫進 IndexedDB，隔天可匯出成 JSON。這是整個專案最大的風險，必須最先驗證。
**依賴**：M1。
**風險**：iOS Safari 對背景或鎖屏頁面的限制最嚴格。
- 🛑 執行前先驗證：iPhone 與 Android 各跑一整晚（插電、螢幕常亮）。量測：麥克風與 AudioContext 能否連續運作 8 小時；通知、來電、誤觸鎖屏時的行為；實際的 `AudioContext.sampleRate`；wake lock 是否被系統收回。**決定規則**：整晚無中斷 → 照目前架構往下做。會中斷但能恢復 → 實作「自動恢復 + 缺口記為未監測時段」。某平台在螢幕常亮下撐不過一晚 → 停下來把結果回報使用者，重新決定該平台是否支援，不自行找替代方案。

### M3 — 背景噪音基準與事件錄製
**交付**：滾動百分位噪音基準、觸發與釋放門檻（遲滯）、最短事件長度、pre-roll / post-roll 環形緩衝、相鄰事件合併，事件 PCM 分塊寫入 IndexedDB。當機恢復：重新整理後發現未完成的當晚資料，讓使用者選擇繼續或直接進入報告。錄音中畫面只顯示「監測中」與經過時間。
**依賴**：M2。
- 🛑 執行前先驗證：門檻、百分位數、時間窗長度要用真實夜晚校準。起始值：基準取 5 分鐘時間窗的第 20 百分位；觸發為基準 +10 dB 且持續 ≥300 ms；釋放為低於基準 +6 dB 持續 2 秒；pre-roll 5 秒、post-roll 3 秒。先用「只記錄幀 dB、不錄音」模式跑一晚。**決定規則**：安靜房間開風扇時每小時誤觸發超過 5 次，觸發門檻每次 +2 dB 再測；同時確認刻意在床邊說話一定會觸發，調高門檻不得犧牲這點。

### M4 — 事件分類（打呼 / 說夢話 / 其他）
**交付**：對每個事件計算規則式頻譜特徵（低頻能量占比、呼吸節律週期性約每 3–6 秒、語音頻帶 300–3400 Hz 能量、3–8 Hz 音節調變），給出分類與信心值。無法確定歸為「其他」。
**依賴**：M3。
- 🛑 執行前先驗證：特徵門檻用使用者自己錄的真實片段調整。**決定規則**：蒐集 M3 錄到的片段，由使用者人工標記至少 20 段，以「打呼與說夢話誤判率低於 20%」為目標調整。達不到就降低信心值，把邊界案例歸為「其他」（準確度優先，召回率次之）。

### M5 — 動作感測（選配）
**交付**：設定頁加入「手機放哪裡」選項（放床上 / 放床頭櫃）。選放床上時在同一個手勢裡請求 DeviceMotion 權限，以 30 秒區間計算動作量並寫入 IndexedDB。拒絕授權或選床頭櫃時只用聲音，流程照常。
**依賴**：M2（可與 M3、M4 平行）。
- 🛑 執行前先驗證：兩個平台實際的 `devicemotion` 事件頻率，以及 wake lock 開著時能否整晚持續收到事件。**決定規則**：事件頻率低於 10 Hz 或會中斷 → 只保留「有無明顯動作」的二元判斷，不計算動作強度。

### M6 — 晨間報告
**交付**：按停止後在本機產生當晚報告：總監測時長、未監測時段、事件時間軸（可點擊播放片段）、各分類次數與總時長、最長事件、背景噪音基準變化曲線。有動作資料時疊上動作量與「疑似淺眠 / 翻身時段」。報告資料結構要同時供畫面、M7 的 `report.md` 與 `data.json` 共用。
**依賴**：M3（M4、M5 完成的話一併呈現）。

### M7 — 匯出與清除
**交付**：用 `fflate` 打包 `report.md`、`data.json`、`night.wav`、`prompt.md`。優先用 Web Share API 分享，不支援就下載。匯出後讓使用者確認，再清除 IndexedDB 裡的當晚資料。
**依賴**：M6。
- 🛑 執行前先驗證：iOS Safari 與 Android Chrome 能否透過 `navigator.share` 分享 zip（Chrome 有檔案類型白名單）。**決定規則**：`navigator.canShare({ files })` 回傳 false 的平台一律走下載，不另寫平台判斷。
- 🛑 執行前先驗證：在 iPhone 上用約 60 MB 的 WAV 打包 zip，量測記憶體與耗時。**決定規則**：會當掉或超過 10 秒 → 改用 fflate 串流 API 分塊打包；仍不行 → 把 `night.wav` 依 30 分鐘切成多個檔案再打包。
